4軸判断基準と5段階の罠 — 本質の理解

> **Origin: DigiCode lineage, preserved via fabcanvas (2026-05).** This educational deep-dive existed in the fabcanvas copy of the rule system (as rules 19/20 of that era) and was later superseded in DigiCode's numbering by other rules — the content itself was too valuable to lose, so it lives on here as a reference companion to `common/14-decision-framework.md`. Real incidents cited are from DigiCode; treat them as worked examples.

これは何か
設計判断で「なんとなく良さそう」「全部大事だから全部やろう」という思考停止を防ぐためのフレームワーク。チェックリストではない。思考のレンズである。

まず、よくある誤解を潰す
❌ 誤解1:「4軸を順番にチェックすればいい」
これはチェックリストではない。「軸1✅ 軸2✅ 軸3✅ 軸4✅」と書いた瞬間、それは何も考えていないのと同じ。
✅ 正しい使い方: 「この判断は軸1（システム安定性）に照らすと具体的にどう影響するか」を言語化する。言語化できないなら、まだ判断する準備ができていない。
❌ 誤解2:「4軸全部満たせば正解」
4軸はトレードオフを可視化する道具。全部満たせることは稀で、満たせると思ったならどこかの評価が甘い。「軸1と軸2が衝突している。軸1を優先する理由はこうだ」と言えることが正しい使い方。
❌ 誤解3:「軸の番号が優先順位」
軸1が最優先なのは事実だが、「だから軸1だけ見ればいい」は軸絶対化の罠（5段階の罠その1）。軸1を満たすために軸2を完全に無視した結果、メンテナンス不能なコードが生まれた実例がある。
❌ 誤解4:「罠を知っていれば罠にかからない」
罠は「知っている」だけでは防げない。DigiCodeプロジェクトでは、罠を明文化したルールを作った直後にそのルールを無視して同じ罠にかかった（rule 16作成直後にrule 16未参照で64 block追加→passRate 88%退行）。知識と実践は別物。

4軸の本質
軸1: システム安定性（最優先）
問い: この判断で、システムが壊れる可能性はあるか？
「壊れる」は広い。コンパイルエラー、実行時クラッシュ、データ消失、セキュリティホール、全部含む。
実例（DigiCode）: pump経路がproductionでdead（registerPumpable呼出0件）なのに25セッション放置。サーボモーターのHW write経路が完全に死んでいた。「コンパイルは通る」「テストは通る」が、実機で物理的に動かない。軸1の「安定性」はテストの通過ではなく、ユーザーが期待する動作が実際に起きるかまで含む。
よくある失敗: 「テスト通ったから安定している」→
テストが見ていない経路が壊れている。テストの通過はシステム安定性の必要条件であって十分条件ではない。
軸2: メンテナンス性（ROI評価）
問い: この判断で、将来の自分（または後任）は困るか？
メンテナンス性は「きれいなコード」の話ではない。変更コストの予測の話。
実例（DigiCode）: setCheck（型チェック）を個別blockごとに場当たり的に修正し続けた結果、168件のsingleton setCheckが散在。1件修正するたびに「他に同じ問題がないか」を全件調査する羽目になった。最終的にscrubNakedValueの1箇所overrideで構造的に全件解消。最初からそうすべきだった。
ROI評価の意味: 「今30分かけて構造的に直す」vs「今5分で場当たり修正して、将来同じ問題が出るたびに30分かける」。どちらのROIが高いかを判断する。
軸3: リリース前タイミング（後で困難なら今潰す）
問い: これをリリース後に直すのは、リリース前に直すより何倍大変か？
「後でやる」は禁句ではない。本当に後で簡単にできることは後でいい。問題は「後で困難になる」ことを「後でやる」に分類してしまうこと。
実例（DigiCode）: attach時の90°強制移動（ピクつき真因1）をPhase Eの前に修正した。リリース後に修正すると、ユーザーが「電源ON時にサーボが指定位置に移動する」という挙動に依存したプログラムを書いている可能性があり、破壊的変更になる。リリース前なら「新しい仕様です」で済む。
判断基準: 「この変更はAPIの契約を変えるか？」YES→リリース前に潰す。NO→後でもいい。
軸4: フレームワーク独立性（緩い軸）
問い: この判断で、特定のフレームワーク/ライブラリに依存度が上がるか？
これは緩い軸。他の3軸と同列に扱わない。フレームワーク依存を完全に排除することは非現実的だし、そもそもフレームワークを使っている時点で依存している。
この軸が効くとき: フレームワークのメジャーバージョンアップやEOLが近い場合、または代替が容易な部分で不必要に深い依存を作ろうとしている場合。
この軸が効かないとき: 「React依存だからVueに移行できるようにしよう」のような過剰な抽象化。そんな移行は99%起きない。

5段階の罠 — 具体例で理解する
罠1: 軸絶対化
症状: 1つの軸だけで全判断を正当化する。
実例: 「軸1（安定性）が最優先だから、テストが全部通るまで何もリリースしない」→
テストを追加し続けて永遠にリリースできない。安定性は最優先だが、安定性の定義が「テスト100%通過」に固定されているのが問題。ユーザーにとっての安定性は「使えること」。
見分け方: 他の軸を検討した形跡がない判断は軸絶対化を疑え。
罠2: 完璧混同
症状: 全軸を満たそうとして判断が遅れる、または全軸を満たしていると錯覚する。
実例: 「軸1も軸2も軸3も軸4も問題ない、完璧な設計だ」→
実は軸2の評価が甘く、後で修正に3セッションかかった。全軸OKと言えるのは、各軸の評価を具体的に言語化した場合のみ。
見分け方: 「全部✅」と書かれていたら疑え。どこかの評価が浅い。
罠3: 時間軸見落とし
症状: 「今」の評価だけで判断し、将来の状態変化を考慮しない。
実例: 「今はユーザー10人だからこの設計で十分」→ 100人になったとき全面書き直し。軸3（リリース前タイミング）は「今 vs 将来」の比較を強制する軸だが、この軸自体を見落とすと時間軸が消える。
見分け方: 判断に「今は」「現時点では」が含まれていたら、「将来は？」と問え。
罠4: Framework見落とし
症状: 特定フレームワーク前提の判断を、汎用的な判断だと思い込む。
実例: 「BlocklyのsetCheckで型安全性を担保する」→ Blocklyのバージョンアップでconnection checkerの挙動が変わり、全件再検証が必要になった。フレームワーク固有のAPIに深く依存した判断は、フレームワーク変更時に全崩壊する。
見分け方:
判断の根拠に固有名詞（Blockly、React、ESP32Servo等）が含まれていたら、その固有名詞が変わったときどうなるかを考えよ。
罠5: 緩い軸の誤運用
症状: 軸4（フレームワーク独立性）を軸1（安定性）と同じ重みで扱う。
実例: 「ESP32Servoライブラリに依存しないように抽象化レイヤーを入れよう」→ 抽象化のバグでサーボが動かない。軸4の「独立性」を追求した結果、軸1の「安定性」が毀損された。緩い軸は他の軸を犠牲にしてまで追求するものではない。
見分け方: 軸4を理由に工数を追加する判断は、「その工数で軸1〜3が改善するか？」と問え。改善しないなら過剰。

実際の使い方（思考プロセスの例）
場面: 「orphan blockがC++ syntax errorを起こす。どう直す？」
ダメな思考（チェックリスト化）
軸1: 安定性に影響する → 直す ✅ 軸2: メンテナンス性 → まあ大丈夫 ✅ 軸3: リリース前 → 今直す ✅ 軸4:
フレームワーク依存 → 特になし ✅ → 結論: 直す
これは何も考えていない。「直す」のは当然として、どう直すかの判断に4軸を使うべき。
良い思考（レンズとして使う）
軸1（安定性）: orphan blockのfile scope
emitは2件のfailだが、同じメカニズムで今後も発生し得る構造的問題。個別修正（Option
B）では構造的リスクが残る。scrubNakedValue override（Option A）なら全件を構造的に予防できる。軸1でOption A優位。
軸2（メンテナンス性）: Option Bは168件のsetCheck singleton cluster全件にメンテナンスコストが永続する。Option
Aは1箇所の修正で完結、メンテナンスコストゼロ。軸2でOption A圧倒的優位。
軸3（タイミング）:
scrubNakedValueのoverride自体は後からでも可能（API契約変更ではない）。ただしリリース前にやれば1000-case 100%でリリース
できる。リリース後にやると「99.8%でリリースした」という事実が残る。軸3で「やるなら今」が若干優位だが、強い差ではない。
軸4（FW独立性）: scrubNakedValueはBlockly固有API。ただしOption
BのsetCheckもBlockly固有。どちらもBlockly依存度は同等。軸4で差なし。
→ 結論: Option A。軸1+軸2で明確に優位、軸3で若干優位、軸4で差なし。
この思考プロセスが「レンズとして使う」ということ。

Self-check用の問い
判断を下す前に、以下を自問する:
1. 各軸で具体的にどう影響するか、言語化できたか？ — 「✅」と書くだけなら考えていない
2. トレードオフは明示されているか？ — 全軸OKなら評価が甘い
3. 5段階の罠のどれかに該当していないか？ — 特に「軸絶対化」と「完璧混同」は頻発する
4. この判断を3ヶ月後の自分が見て、なぜそう判断したか理解できるか？ — 言語化が不十分なら記録も不十分
5. founding use case（プロジェクトの核心目標）との関係は明示されているか？ —
「何のためにこの判断をしているのか」が消えていないか
