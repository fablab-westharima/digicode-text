# Rule: i18n — Canonical Source, Labels Injection, 5-Language Same-Commit, Value≠Key

> **Origin: DigiCode (2024–2026).** This rule was battle-tested on a real project; the incidents cited (BUG-XXX / Session NNN / case N) are preserved verbatim as reference lessons — real failures carry a weight hypotheticals don't. When applying in your project: treat origin-specific paths, URLs, commands, and stack names as worked examples and substitute your own; append your project's cases below the originals — never delete them.

**Severity:** ★★★★
**Scope:** common (DigiCode-specific bits in `digicode/09-backend-i18n.md`)
**Last reviewed:** 2026-04-26
**Related memory:** `i18next_explicit_variants`, `util_i18n_labels_injection`
**Related cases:** BUG-008 (dvMismatch 3 → 0), BUG-009/009b (state machine i18n), BUG-015 (conversationExporter), BUG-024 (backend 213 sites + 745 translations), BUG-036 (nonExplicitSupportedLngs trap), BUG-037 (AdminPage 542 lines), BUG-039 (1-3 lines → 2,235 translations), BUG-040 (brand terms not translated)

---

## TL;DR

1. **5 languages, same commit. Always.** ja / en / es / pt-PT / zh-TW. No "translate later" — that's how 379 hardcoded JP strings accumulated pre-Phase 17.
2. **Canonical JA source for big content.** `data/tutorials.ts`, `data/sampleProjects.ts`, `pages/about/AboutPageJa.tsx`, store definitions. Non-JA goes in `*I18n.ts` overrides.
3. **`audit-i18n.js` must pass:** Keys missing 0, dvMismatch 0. Run before commit.
4. **Util / non-React i18n: labels-object injection pattern.** Pure utils take `labels: { ... }` and `locale: string` from caller. Don't import `useTranslation` in utils.
5. **Brand terms don't translate** (DigiCode, AI, Humanoid, Transform, Wheel, technical units). Translating these creates inconsistency — see `digicode/02-brand-terms.md`.
6. **Key existence ≠ value translated.** Run a `same-as-en` audit on non-English locales. BUG-039 had 749 untranslated values per language with all keys present.
7. **`nonExplicitSupportedLngs: false`** when `supportedLngs` includes 5-letter codes (`pt-PT`, `zh-TW`). The default `true` triggers an undocumented variant→main reduce that fails.

## Why this exists

- **Phase 17 cleanup** (2026-04-19): 554 → 379 hardcoded JP after a massive sweep. Establishes "ルール 33: 5-language same commit" as project policy.
- **BUG-036** (2026-04-24): pt-PT and zh-TW silently fell back to English. Root cause: `nonExplicitSupportedLngs: true` causes `pt-PT → pt` reduce inside i18next; `pt` not in `supportedLngs` → fallback. Public docs only describe main→variant direction. 1-line fix (`true → false`) resolved entire i18n flow.
- **BUG-015** (Phase 7): `conversationExporter.ts` was hardcoded JP because utils can't call `useTranslation()`. Solution: caller resolves `t(...)` and passes `labels: ExportLabels` + `locale: string` to the util. Pattern usable for any util/service/store.
- **BUG-009 → 009b** (Phases 7/8): EditorPage compile log used `compileLog.some(log => log.includes('[接続確認]'))` — i18n breaks this. Refactored into `compileLogMeta: { hasConnectionCheck, hasCodeAnalysis, hasError }` flag base. See `common/10-state-machine.md`.
- **BUG-039** (A Phase): bug file said "minor 1-3 line fix." Reality: 2,235 translations across 3 languages. The 5-language *value* comparison revealed `same-as-en = untranslated` for 749 strings/lang. Key existence != value populated.
- **BUG-024** (A Phase): 213 backend errors hardcoded JP. Solution = inverse of frontend pattern: middleware injects locale into `c.set('locale')`, helper `errorJson(c, key, status)` resolves at response time. See `digicode/09-backend-i18n.md`.

## When to apply

- Adding any user-visible string.
- Touching `i18n/locales/*.json`.
- Touching components that call `t(...)`.
- Refactoring state machines that match user-visible strings.
- Adding a new language or upgrading i18next.

## How to apply

### Frontend: standard `t()` usage

```typescript
import { useTranslation } from 'react-i18next';

function MyComponent() {
  const { t } = useTranslation();
  return <button>{t('myComponent.save', { defaultValue: '保存' })}</button>;
}
```

- `defaultValue` is the **JA fallback** (canonical JA source policy).
- 5 locale files all need the key:

```json
// ja.json
{ "myComponent": { "save": "保存" } }

// en.json
{ "myComponent": { "save": "Save" } }

// es.json
{ "myComponent": { "save": "Guardar" } }

// pt-PT.json
{ "myComponent": { "save": "Guardar" } }

// zh-TW.json
{ "myComponent": { "save": "儲存" } }
```

### Util / service / store: labels-object injection

When the function isn't inside React (utils, services, Zustand stores):

```typescript
// services/foo/exporter.ts (pure utility)
export interface ExportLabels {
  title: string;
  date: string;
  // ...
}

export interface ExportOptions {
  labels: ExportLabels;
  locale: string; // e.g., 'ja-JP', 'en-US'
  // ...
}

export function exportToMarkdown(data: Data, opts: ExportOptions): string {
  const dateStr = new Date().toLocaleDateString(opts.locale);
  return `# ${opts.labels.title}\n\n**${opts.labels.date}**: ${dateStr}\n...`;
}
```

```typescript
// component (caller resolves t before invoking the util)
const { t, i18n } = useTranslation();
const localeMap: Record<string, string> = {
  ja: 'ja-JP', en: 'en-US', es: 'es-ES', 'pt-PT': 'pt-PT', 'zh-TW': 'zh-TW',
};
exportToMarkdown(data, {
  labels: {
    title: t('foo.export.title'),
    date: t('foo.export.date'),
  },
  locale: localeMap[i18n.language] ?? 'en-US',
});
```

Test util with mock labels — no i18n setup required.

### canonical JA source for big content

For data files with 50+ entries that change frequently (tutorials, samples, store seeds):

- Write JA inline in `data/foo.ts`.
- Provide non-JA overrides in `data/fooI18n.ts` keyed by id.
- Lookup at runtime: `i18n.language === 'ja' ? base.title : (overrides[lang]?.[id]?.title ?? base.title)`.
- New entry: only JA required to ship. Other languages can be added later without blocking the feature.

`audit-i18n.js`'s `EXCLUDE_PATTERNS` skips canonical JA files so the CJK chars don't trip the hardcoded-JP detector.

### Pre-commit i18n checks

```bash
# All keys present in all locales, defaultValues match
node scripts/audit-i18n.js
# Expected: Keys missing 0 / dvMismatch 0

# Optional: same-as-en value audit (DIY for now; BUG-045 pending)
# Compares en.json values to es/pt-PT/zh-TW.json values.
# Equal value (e.g., "Wait" in es.json) usually = untranslated.
```

### `nonExplicitSupportedLngs` configuration

When `supportedLngs` lists explicit 5-letter codes:

```typescript
// variants/ota/frontend/src/i18n/index.ts
i18n.use(LanguageDetector).use(initReactI18next).init({
  resources,
  supportedLngs: ['ja', 'en', 'es', 'pt-PT', 'zh-TW'],
  nonExplicitSupportedLngs: false, // ← MUST be false (BUG-036)
  fallbackLng: 'en',
  load: 'currentOnly',
  detection: { order: ['localStorage', 'navigator'], caches: ['localStorage'] },
});
```

If you set `true`, `i18n.changeLanguage('pt-PT')` internally reduces to `pt`, which isn't in `supportedLngs`, fallback fires, English shows up. `false` is the safe default for explicit 5-letter codes.

### Brand-term policy

Don't translate:
- Product names: `DigiCode`, `Humanoid`, `Transform`, `Wheel`
- AI/ML brand: `AI` (not `IA`)
- Technical units: `I2C`, `SPI`, `UART`, `MQTT`, `HTTP`, `PWM`, `ESP32`, `ms`, `Hz`, `V`
- Chip / sensor names: `DFPlayer`, `NeoPixel`, `MPU6050`, `BME280`
- Musical notes: `A`, `B`, `C`, `D`, `E`, `F`, `G`
- mdi icon refs: `fan`, `lightbulb`, `play`

Do translate:
- All natural-language nouns / verbs / adjectives
- Common words even when 1 character lowercase (color names, action words like `forward`/`backward`, status like `Red`/`Sad`)

(Real case BUG-039 補完: `^[a-z]+$` regex was over-aggressive for 1-word lowercase classifier — flagged "angle"/"forward"/"Red" as technical. Fixed via 153-translation supplement.)

### State machines must not depend on translatable strings

```typescript
// Bad: i18n breaks the predicate
{compileLog.some(log => log.includes('[接続確認]')) && <Panel />}
// → after i18n, log shows '[Connection Check]' / '[連線檢查]' — predicate fails

// Good: flag-based state
const [compileLogMeta, setCompileLogMeta] = useState({
  hasConnectionCheck: false, hasCodeAnalysis: false, hasError: false,
});
const addLog = (msg: string, opts?: { phase?: 'connection-check'; isError?: boolean }) => {
  setCompileLog(prev => [...prev, msg]);
  if (opts?.phase === 'connection-check') setCompileLogMeta(m => ({ ...m, hasConnectionCheck: true }));
};
{compileLogMeta.hasConnectionCheck && <Panel />}
```

(Real case: BUG-009b refactor in Phase 8.)

## Anti-patterns

### ❌ "Translate later"

```
Bad: ship JA only, file a TODO ticket "translate to 4 langs."
Good: 5 languages in the same commit. If 4 langs delay the release, fix scope.
```

### ❌ Trusting key presence as proof of translation

```
Bad: en.json and es.json both have key foo.bar → assume translated.
Good: compare values — if es.json's value === en.json's value (and not a brand term), it's untranslated.
```

### ❌ `useTranslation` in a util / service

```typescript
// Bad
import i18n from '@/i18n';
export function formatThing(data: Data) {
  return i18n.t('foo.format', { ... });  // tight coupling to React tree, hard to test
}

// Good — caller does i18n, util takes labels
export function formatThing(data: Data, labels: { format: string }) { ... }
```

### ❌ Hardcoded `'ja-JP'` for `toLocaleDateString`

```typescript
// Bad
new Date().toLocaleDateString('ja-JP', { ... });  // ignores user's chosen language

// Good
const localeMap: Record<string, string> = {
  ja: 'ja-JP', en: 'en-US', es: 'es-ES', 'pt-PT': 'pt-PT', 'zh-TW': 'zh-TW',
};
new Date().toLocaleDateString(localeMap[i18n.language] ?? 'en-US', { ... });
```

(BUG-037 fix in AdminPage.)

### ❌ Translating brand terms

```
Bad: Spanish UI says "Chat IA" while Japanese says "AIチャット" → brand inconsistency.
Good: All 5 langs use "AI Chat" / "AIチャット" / "AI 對話" — keep "AI" untranslated.
```

(BUG-040.)
