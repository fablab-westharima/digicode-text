- 🟡 **未確認**: ブラウザから Anthropic API を直接叩く場合、通常は `anthropic-dangerous-direct-browser-access` ヘッダが要る。`anthropicClient.ts` の grep では当該ヘッダが見つからなかった。**実行していないので動作は未verify** — Text で同方式を採る前に要確認 (追加調査必要)。
- 🟡 localStorage に API key を平文保存する設計上のリスクは donor と共通。Text も同じ選択をするなら、**同じリスクを継承する**という認識が要る (XSS 一発で鍵が抜ける)。

## 2. AI dictionary の実体

**`public/ai/block-catalog.json` — 379,375 bytes、生成物** (`"generatedAt": "2026-06-04T18:00:24.862Z"`)。1 block = 1 エントリで `type / category / tooltip / colour / isStatement / hasOutput / modes[] / boardRequires / fields[] / valueInputs[] / statementInputs[]` を持つ。

- 実行時に `fetch('/ai/block-catalog.json')` して**モジュール内変数にキャッシュ** (`systemPrompt.ts:86-95`)。
- `filterCatalog()` は **mode / board を受け取るが無視して全 block を返す**（意図的な設計判断と注記あり、`systemPrompt.ts:98-105`）。
- few-shot は `data/sampleProjects.ts` から `fewShotSelector.ts` が選ぶ (`systemPrompt.ts:111-135`)。
- board context は `BoardDefinition` をそのまま渡す (`index.ts:49`)。

→ **辞書は「生成された JSON を実行時 fetch し、system prompt へ整形して差し込む」というパイプライン**。この**構造は Text へそのまま移せる**。中身 (block catalog) が Text 用辞書 (Board / Device / Library API / sample / DigiCode Text 機能一覧) に置き換わるだけ。

## 3. 出力と検証パイプライン — ここが最大の資産であり、最大の非互換

`GenerateOutput = { xml: 検証済み Blockly XML, rawResponse, attempts (1-3) }` (`index.ts:38-42`)。

検証系のファイル構成:

| ファイル | 役割 |
|---|---|
| `xmlValidator.ts` | Blockly XML の構文検証 |
| `semanticValidator.ts` | 意味検証 |
| `blocklyDryRun.ts` | **実際に Blockly へ流して通るか試す** |
| `jsonValidator.ts` | JSON 応答検証 |
| `validationRetryOrchestrator.ts` | 検証失敗 → 再プロンプト → 最大 3 回 |
| `fixPromptBuilder.ts` | 修正指示プロンプト生成 |
| `retryHelper.ts` / `errors.ts` | 再試行・エラー分類 |
| `conversationContext.ts` / `conversationExporter.ts` | 文脈管理・書き出し |

**評価:** 「生成 → 機械検証 → 失敗なら文脈付きで再生成 → 上限で諦める」という **generate-validate-retry の骨格は Text でも必要**で、そのまま設計を継承できる。一方 **検証器そのものは Blockly XML 専用**であり Text では使えない。Text 版の等価物は「**実際に compile が通るか**」であり、donor には既に compile API があるため、`blocklyDryRun` の位置に **compile dry-run** を置く形が構造的な対応物になる (提案であり、architecture 確定ではない)。

## 4. 現状 AI が持っていない / Text で新規実装が必要なもの

- **multi-file context** — `ChatInput` は `messages / mode / language / robotMode / board / controllerSchema` のみ。ファイル集合という概念が無い (`index.ts:44-55`)。
- **related-file discovery / diff / patch / edit application** — 該当実装なし。出力は XML 一括置換モデル。
- **compile error → 修正ループ** — `fixPromptBuilder` は**検証失敗**に対する修正であり、**compile エラー**を入力にする経路は確認できていない (追加調査必要)。
- **external code analysis / Block への変換** — 企画書が「既存機能」として挙げるが、本セッションでは該当実装を特定できていない (**追加調査必要**。`blockGen` mode 以外の経路が別にある可能性)。

## 5. verdict

| 対象 | verdict | 根拠 |
|---|---|---|
| user API key + localStorage + ブラウザ直接呼び出しの方式 | **そのまま流用可能** | 企画方針と一致、backend 依存なし |
| provider 抽象 (`AiProvider` 4 種 + client 2 実装) | **そのまま流用可能** | Blockly 非依存 |
| 辞書パイプライン (生成 JSON → 実行時 fetch → prompt 整形) | **改修流用** | 構造は流用、中身は総入れ替え |
| few-shot selector + sampleProjects | **改修流用** | 仕組みは有効、サンプルは Text 用に作り直し |
| generate-validate-retry orchestrator | **改修流用** | 骨格は流用、検証器を差し替え |
| `xmlValidator` / `semanticValidator` / `blocklyDryRun` | **Text では不採用** | Blockly XML 専用 |
| `block-catalog.json` とその生成スクリプト | **Text では不採用**（生成の**考え方**のみ流用） | 中身が block 定義 |
| project-aware AI (multi-file / diff / patch) | **新規実装が必要** | donor に存在しない |
| compile error 修正ループ | **追加調査必要** | 経路を特定できていない |
| 外部コード解析・変換機能 | **追加調査必要** | 実装を特定できていない |

## 6. risk / remaining unknown

- 🔴 **project-aware AI は donor に前例が無い**。企画の中核機能でありながら**新規設計が必要**な最大領域。AI が multi-file を壊さないことの acceptance (裁定 §16 の AI scenario test) も、donor に参照実装が無い。
- 🟡 ブラウザ直接呼び出しの CORS / ヘッダ要件が未verify。
- 🟡 localStorage 平文保存のリスクを Text も継承するかは設計判断 (Human 裁定候補)。
- 🟢 AI 経路に auth / 課金の結合が無いため、Classic の auth/課金を落としても AI は成立する。
