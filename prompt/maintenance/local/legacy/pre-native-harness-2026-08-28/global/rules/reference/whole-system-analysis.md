「何度直しても直らない」の正体 — 局所修正の罠と全体視点の回復

> **Origin: DigiCode lineage, preserved via fabcanvas (2026-05).** This educational deep-dive existed in the fabcanvas copy of the rule system (as rules 19/20 of that era) and was later superseded in DigiCode's numbering by other rules — the content itself was too valuable to lose, so it lives on here as a reference companion to `common/14-decision-framework.md`. Real incidents cited are from DigiCode; treat them as worked examples.

この文書の目的
修正を繰り返しても問題が解決しない状況に陥っている場合、それは技術力の問題ではなく視野の問題である。本文書は、局所修正の罠のメカニズムを解明し、全体視点を回復するための具体的な行動指針を示す。

局所修正の罠とは何か
「このファイルのこの行を直せば動くはず」→ 直した → 動かない → 「じゃあこっちも直そう」→ 直した → 別の場所が壊れた →
「じゃあそっちも...」
このループの本質は修正ではなくモグラ叩きである。1つ叩くと別の穴から出てくる。なぜか？ モグラの巣（=
根本原因）を見ていないからだ。

なぜ局所修正を繰り返すのか
理由1: 「見えている症状」と「原因」を混同している
バグ報告は常に症状として届く。「画面にグレーの縦線が出る」「コンパイルエラーになる」「サーボが動かない」。これらは症状
であって原因ではない。
症状に対して直接手を打つ（= 縦線の色を変える、エラーの行を修正する、サーボの初期値を変える）のは、熱がある患者に氷枕を
渡すようなもの。熱は下がるかもしれないが、感染症は治らない。
実例: flyoutの縦線バグ。最初にscrollbar wrapperのbackground-colorを修正 → 効果なし。次にflyout
backgroundのstrokeを疑う → 違った。3回目でChromeのDOM調査を行い、scrollbar
handleが原因と特定。さらに調査を進め、scrollbar
SVGがflyout外に配置されるBlocklyの設計上の問題と判明。最初にDOM調査をしていれば、3回の無駄な修正は不要だった。
理由2: 修正の影響範囲を確認していない
1箇所を直したとき、「この修正の影響を受ける他の箇所はどこか」を確認していない。
実例: scrubNakedValueのoverrideをBlocklyEditor.tsxに追加した。ブラウザでは動く。だが1000-caseのorchestrator（headless
Node.js環境）はBlocklyEditor.tsxを読み込まない。cpp-generator.tsという別ファイルからjavascriptGeneratorを使っている。c
ommit前に気づいたから良かったが、気づかなければ「直したのに1000-caseで同じエラーが出る」というモグラ叩きの一手になって
いた。
理由3: 「動いた」を「直った」と混同している
修正後に目の前の症状が消えると「直った」と思う。だが、それは「目の前の症状が消えた」であって「原因が解消された」ではな
い。
実例: pump経路がproductionでdead（registerPumpable呼出0件）なのに、walkBlockingは時間経過でreturnする。つまり「ブロッ
クを実行したら完了して戻ってきた」ように見える。だがサーボは90°のまま物理的に動いていない。「関数がreturnした =
機能が動作した」という即断は、「dialog save成功 = 機能完成」と同じ罠。
理由4: 推測で修正している
原因を特定せずに「たぶんここだろう」で修正を始める。推測が当たれば1回で済むが、外れると推測→修正→確認→外れ→推測→修正..
. の無限ループに入る。
実例: flyout縦線の原因候補を4つ挙げた段階で、候補Aが「最有力」だからとCSS修正を実行 → 効果なし。候補Bも推測で修正 →
効果なし。最終的にChrome DevToolsでelementsFromPointを使って実DOM要素を特定して初めて、原因がscrollbar
handleだとわかった。推測で修正するな。まず原因を確定させろ。

「全体を見る」とは具体的に何をすることか
「全体を見ろ」は抽象的すぎて行動に移せない。以下は具体的な行動指針。
行動1: 修正する前に、影響を受ける全ファイルを列挙する
コードを書く前に、grepする。
「この関数を呼んでいる箇所はどこか」「この変数を参照している箇所はどこか」「このCSSクラスが適用される要素はどこか」。
列挙してから修正を始める。列挙せずに修正を始めるのは、地図を見ずに運転するのと同じ。
# 修正前に必ず実行する問い
1. この修正の影響を受けるファイルは何か？ → grep
2. この修正と対になる修正（ペア修正）はあるか？
3. この修正でテストの期待値は変わるか？
4. この修正はブラウザだけでなく、headless環境・CI・production全てで効くか？
行動2: 修正の前に原因を確定させる
修正と調査を同時にやらない。まず調査だけを行い、原因を確定させてから修正に入る。
# 調査と修正の分離プロトコル
Step 1: 調査（修正するな、事実のみ報告）
  - 症状のverbatim記録
  - 関連コードのgrep結果
  - データフロー/呼出経路のtrace
  - 原因候補の列挙（1つに絞るな）

Step 2: 原因確定（推測を事実と混同するな）
  - 各候補の検証手段を明示
  - 検証結果をverbatimで報告
  - 「確定」と「推察」を明示的に分離

Step 3: 修正計画（ユーザー承認後に着手）
  - 修正内容
  - 影響範囲
  - 副作用評価
  - ペア修正の有無

Step 4: 実装（計画通りに実行）
行動3: 「同じ手法で他にも問題がないか」を問う
1件の問題を見つけたら、同じメカニズムで発生し得る他の問題を全件探す。
実例: case_0447（json_simple + math_number）とcase_0584（array_content）は、両方とも「setCheck
rejectでorphan化したblockがscrubNakedValueでfile scope emitされる」という同じメカニズム。case_0447だけ直してcase_0584
を見逃すのは「1件修正して安心する」パターン。grepで同じメカニズムの全件を洗い出し、構造的に対策する。
# 1件の問題発見時の問い
1. 同じメカニズムで発生し得る他の問題はあるか？ → grep
2. 個別修正と構造的修正、どちらが適切か？
3. 構造的修正で今後の同型問題を予防できるか？
行動4: 修正後に「本当に直ったか」を多角的に検証する
「修正した → テスト通った → OK」ではない。
# 修正後の検証チェック
1. 修正対象の直接的な症状は消えたか？
2. 修正の副作用で別の症状が出ていないか？
3. テスト環境だけでなくproduction環境でも問題ないか？
4. 同じメカニズムの他のケースも解消されているか？
5. HW連携がある場合、物理的に期待動作しているか？（「コード上は正しい」≠「物理的に動く」）

品質とは何か
品質は「バグがないこと」ではない。ユーザーが期待する動作が、ユーザーが期待するタイミングで、ユーザーが期待する環境で、
確実に起きること。
* コンパイルが通ることは品質ではない。実行して動くことが品質。
* テストが通ることは品質ではない。ユーザーの手元で動くことが品質。
* UIに「保存しました」と表示されることは品質ではない。実際にデータが保存されていることが品質。
* 関数がreturnすることは品質ではない。returnするまでに期待する処理が行われたことが品質。
局所修正を繰り返す人は、品質の定義が「自分の目の前の症状が消えること」に矮小化されている。品質の定義を「ユーザーにとっ
て期待通りに動くこと」に拡張した瞬間、見るべき範囲が自然と広がる。

局所修正ループから抜け出すための原則
原則1: 修正する前に、全体像を把握する時間を取れ
「早く直さなきゃ」という焦りが局所修正を生む。30分の調査で正しい原因を特定すれば、1回の修正で解決する。調査を省いて5分
の推測修正を6回繰り返せば、30分かかった上に問題は解決していない。調査は遅いのではなく、最も速い。
原則2: 1件見つけたら、同種を全件探せ
1件のバグは氷山の一角。同じメカニズムのバグが他にないかを確認してから修正に入る。1件ずつ対処するのはモグラ叩き。巣ごと
潰す。
原則3: 「ここだけ直せば大丈夫」は危険信号
この言葉が頭に浮かんだら、それは影響範囲の確認が不足しているサイン。「ここだけ」と思った範囲の外に影響があるから、何度
直しても直らない。
原則4: 推測で修正するな、事実で修正しろ
「たぶんここが原因」→ 修正 → 違った、のループは全て推測起点。「ここが原因である証拠」を掴んでから修正する。証拠はgrep
結果、DOM調査結果、ログ出力、デバッガのステップ実行など、再現可能な事実のみ。
原則5: 修正1件につき、影響確認を必ずペアにする
修正と影響確認は常にセット。修正だけして影響確認を飛ばすのは、手術して縫合を忘れるのと同じ。
修正 → 直接影響の確認 → ペア修正の確認 → 副作用の確認 → テスト → commit
  ↑ このサイクルを1件の修正ごとに回す。まとめてやらない。

まとめ
やめること    やること
症状を見て即修正    原因を確定させてから修正
1箇所だけ見て修正    影響範囲を全件grepしてから修正
「たぶんここ」で修正    証拠（grep/DOM/log）を掴んでから修正
修正して「動いた」で終了    多角的に検証して「直った」を確認
1件見つけて1件直す    同じメカニズムの全件を探して構造的に直す
「ここだけ直せば大丈夫」    「他に影響する箇所はないか」
局所修正の繰り返しは、技術力の不足ではなく、視野の狭さが原因。
視野を広げるのは難しいことではない。修正する前にgrepする。それだけで局所修正ループの半分は防げる。
